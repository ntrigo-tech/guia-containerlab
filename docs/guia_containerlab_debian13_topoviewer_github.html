01 · Conceptos

¿Qué es Containerlab?

Containerlab es una herramienta open source para definir, desplegar y administrar topologías de red construidas principalmente con contenedores Linux. La topología se describe en un archivo YAML y Containerlab crea los nodos y enlaces usando un runtime de contenedores, normalmente Docker.

Los nodos pueden ser imágenes de sistemas operativos de red, routers virtuales, herramientas Linux, generadores de tráfico, servicios de redes móviles 4G-5G o servicios de infraestructura.

Idea clave: el YAML es la fuente declarativa de la topología. El laboratorio puede desplegarse, destruirse y volver a desplegarse de forma repetible, siempre que las imágenes y las condiciones del host estén disponibles.
02 · Proyecto

Origen y ecosistema

Containerlab nació en el ecosistema de Nokia, impulsado por el equipo relacionado con Nokia SR Linux y publicado como proyecto open source bajo la organización srl-labs en GitHub. No es un producto exclusivo para equipos Nokia: puede trabajar con múltiples tipos de nodos e imágenes, de acuerdo con el soporte y los requisitos de cada imagen.

Containerlab

Interpreta la topología YAML y administra el ciclo de vida del laboratorio.

Docker

Descarga imágenes, ejecuta contenedores y aporta el runtime de red.

GitHub

Hospeda el código, los YAML, documentación, historial y colaboración.

GHCR

GitHub Container Registry almacena y distribuye imágenes de contenedores.

GitHub y GHCR son servicios distintos: un repositorio Git almacena archivos y versiones del proyecto; un paquete GHCR almacena imágenes de contenedores.

03 · Por qué usarlo

Ventajas y límites

REPETIBILIDAD

Topologías como código

La topología queda documentada en YAML, se puede revisar en Git y recrear en otros hosts compatibles.

EFICIENCIA

Menos sobrecarga

Los contenedores suelen consumir menos recursos que una VM completa por nodo, aunque las imágenes de red pueden ser exigentes.

AUTOMATIZACIÓN

CLI e integración

Permite automatizar deploy, inspección, comandos y destrucción de laboratorios mediante scripts y pipelines.

COLABORACIÓN

GitHub y repositorios

Docentes y estudiantes pueden compartir topologías, revisar cambios y trabajar con versiones controladas.

FLEXIBILIDAD

Distintas imágenes

Permite combinar hosts Linux, routers virtuales y herramientas de análisis, según compatibilidad y licencias.

LÍMITES

No es magia

El rendimiento depende de CPU, RAM, disco, kernel, imagen y tipo de tráfico. No todas las funciones de hardware se emulan.

04 · Instalación desde cero

Debian 13: host, Docker y Containerlab

Usá una instalación actualizada de Debian 13, acceso con sudo o root y conectividad a los repositorios. Los comandos siguientes son una ruta práctica; verificá siempre la documentación oficial si cambian los métodos de instalación.

4.1 Actualizar e instalar utilidades

Terminal · Debian
sudo apt update
sudo apt full-upgrade -y
sudo apt install -y ca-certificates curl gnupg git nano iproute2 iputils-ping

4.2 Instalar Docker

Para una instalación sencilla de laboratorio se puede usar el paquete de Debian:

Terminal
sudo apt install -y docker.io
sudo systemctl enable --now docker
sudo docker version
sudo docker run --rm hello-world

Para entornos productivos o para seguir el canal de versiones del proveedor, consultá la guía oficial de Docker Engine para Debian. Evitá mezclar repositorios de distribuciones distintas.

4.3 Instalar Containerlab

El instalador oficial instala Containerlab y puede ofrecer la instalación de Docker y otras herramientas.

Instalador oficial
bash -c "$(curl -sL https://get.containerlab.dev)"
containerlab version
containerlab --help

Alternativamente, seguí la sección de instalación APT del sitio oficial para configurar el repositorio y luego instalar el paquete containerlab. No ejecutes scripts remotos a ciegas en un servidor institucional: revisá su contenido y política de cambios antes.

4.4 Permisos y verificación

Terminal
sudo docker ps
containerlab version
groups

La pertenencia al grupo docker permite controlar Docker y equivale, en la práctica, a privilegios elevados sobre el host. La administración privilegiada de Containerlab también debe limitarse a usuarios de confianza. Cerrá sesión y volvé a entrar si agregás un usuario a un grupo.

Seguridad: no expongas el socket Docker, la API de Containerlab ni una interfaz de laboratorio a Internet sin autenticación, TLS, controles de red y una política de permisos adecuada.
05 · Primer laboratorio

Dos PCs Linux conectadas

Ejemplo mínimo con la imagen ghcr.io/srl-labs/network-multitool. El enlace de datos une pcA:eth1 con pcB:eth1. La interfaz de gestión que crea Containerlab suele ser eth0; el ejemplo asigna IPs de laboratorio a eth1.

5.1 Crear el archivo YAML

Creá un directorio de trabajo y guardá el siguiente contenido como dos-pcs.clab.yml.

dos-pcs.clab.yml
name: dos-pcs

topology:
  nodes:
    pcA:
      kind: linux
      image: ghcr.io/srl-labs/network-multitool
      exec:
        - ip link set eth1 up
        - ip address add 10.0.0.1/24 dev eth1

    pcB:
      kind: linux
      image: ghcr.io/srl-labs/network-multitool
      exec:
        - ip link set eth1 up
        - ip address add 10.0.0.2/24 dev eth1

  links:
    - endpoints: ["pcA:eth1", "pcB:eth1"]
Nota sobre la imagen: el ejemplo presupone que la imagen arranca con una shell compatible y que la interfaz de datos se llama eth1. Si una versión concreta de la imagen o del runtime presenta otro comportamiento, comprobá las interfaces con ip -br addr y ajustá el YAML. La etiqueta latest puede cambiar; para prácticas reproducibles, fijá una versión o digest verificado.

5.2 Desplegar y probar

Terminal
mkdir -p ~/labs/dos-pcs
cd ~/labs/dos-pcs
# Guardar aquí dos-pcs.clab.yml
sudo containerlab deploy -t dos-pcs.clab.yml
sudo containerlab inspect -t dos-pcs.clab.yml
sudo docker exec -it clab-dos-pcs-pcA ping -c 4 10.0.0.2
sudo docker exec -it clab-dos-pcs-pcB ip -br addr

Containerlab descarga la imagen si no está localmente disponible. El nombre habitual de los contenedores incluye el prefijo del laboratorio, por ejemplo clab-dos-pcs-pcA; verificá el nombre real con docker ps.

5.3 Destruir el laboratorio

Terminal
sudo containerlab destroy -t dos-pcs.clab.yml
06 · Interfaz gráfica

TopoViewer y la interfaz web

TopoViewer: interfaz web para visualizar y gestionar las topologías de Containerlab.
Backend/API: servicio al que se conecta la interfaz para realizar las operaciones.
Host Linux: equipo donde se ejecutan Containerlab, Docker y los nodos del laboratorio.
Usuarios: el procedimiento de alta depende de la implementación concreta de TopoViewer; no corresponde asumir que utiliza los grupos clab_api y clab_admins de otra solución.

6.1 Instalar la API oficial en el host de laboratorio

Debian · Host Linux
curl -fsSL https://raw.githubusercontent.com/srl-labs/clab-api-server/main/install.sh | sudo bash -s -- install
sudoedit /etc/clab-api-server/clab-api-server.env

Revisá como mínimo la dirección anunciada por la API (API_SERVER_HOST), el secreto JWT generado por el instalador y CORS_ALLOWED_ORIGINS cuando una interfaz web en otro origen deba comunicarse directamente con la API. No publiques el secreto JWT ni lo incluyas en Git.

6.2 Iniciar y verificar el servicio

Terminal
sudo systemctl enable --now clab-api-server
sudo systemctl status clab-api-server
sudo journalctl -u clab-api-server -n 100 --no-pager

6.3 Ejecutar la interfaz web oficial

Terminal · Docker
sudo docker run -d --name containerlab-app \
  --restart unless-stopped \
  --network host \
  ghcr.io/srl-labs/containerlab-web:latest

Desde un navegador que pueda alcanzar el servidor, abrí https://IP-O-DNS-DEL-HOST:3001. La imagen usa HTTPS con certificado autofirmado por defecto, por lo que el navegador puede mostrar una advertencia. Si la web y la API están en el mismo host, el endpoint predeterminado suele ser https://localhost:8090 desde el punto de vista del servidor web; si están separados, usá un nombre DNS o IP alcanzable desde la aplicación web.

No confundir productos: estos pasos corresponden a Containerlab App + clab-api-server. No son instrucciones universales para instalar una distribución de TopoViewer de terceros o de una universidad.
07 · Acceso y permisos

Crear usuarios para la interfaz web oficial

En Containerlab App oficial no se crean cuentas independientes dentro de la interfaz: la autenticación se apoya en usuarios Linux/PAM del host donde se ejecuta clab-api-server. El instalador crea los grupos clab_api y clab_admins si no existen.

7.1 Crear un usuario Linux

Ejemplo: usuario alumno01
sudo adduser alumno01
sudo usermod -aG clab_api alumno01

El usuario inicia sesión con su nombre y contraseña Linux. La pertenencia a clab_api permite el acceso estándar a la API. Para aplicar cambios de grupo, cerrá y volvé a iniciar la sesión cuando corresponda.

7.2 Permisos administrativos

Solo para operadores autorizados
sudo usermod -aG clab_admins operador01

Advertencia: los miembros de clab_admins tienen permisos elevados para administrar laboratorios. No agregues estudiantes a ese grupo salvo que deban tener privilegios administrativos.

7.3 Modelo mental de permisos

Elemento Función Recomendación
Cuenta Linux Identidad y autenticación PAM Una cuenta individual por usuario; evitar cuentas compartidas.
clab_api Permite acceder a la API Grupo habitual para alumnos y operadores con permisos estándar.
clab_admins Permisos elevados sobre los laboratorios Reservar para administradores de confianza.
~/.clab Directorio de laboratorios del usuario por defecto Respaldar archivos importantes y documentar políticas de cuotas.

Si tu TopoViewer institucional tiene su propio sistema de usuarios, los pasos pueden ser distintos. No reutilices las instrucciones de grupos Linux sin confirmar qué backend de autenticación usa esa instalación.

08 · Git, GitHub y GHCR

Cómo usar GitHub con Containerlab

GitHub sirve para versionar y compartir el código del laboratorio; GHCR (GitHub Container Registry) permite publicar imágenes personalizadas. No es obligatorio publicar la imagen: se puede usar una imagen pública existente, como ghcr.io/srl-labs/network-multitool.

8.1 Crear un repositorio para el laboratorio

  1. Creá un repositorio en GitHub, por ejemplo containerlab-dos-pcs.
  2. Guardá el YAML, un README con requisitos y los comandos para desplegar/destruir.
  3. Inicializá Git, confirmá el cambio y publicá el repositorio.
Desde el directorio del laboratorio
cd ~/labs/dos-pcs
git init
git add dos-pcs.clab.yml
git commit -m "Agrega laboratorio de dos PCs"
git branch -M main
git remote add origin https://github.com/USUARIO/containerlab-dos-pcs.git
git push -u origin main

Reemplazá USUARIO por tu cuenta u organización y configurá la autenticación de GitHub (por ejemplo, mediante SSH o un método de credenciales admitido). No pongas contraseñas ni tokens en el YAML o en el repositorio.

8.2 Clonar y desplegar desde otro host

Otro Debian con Containerlab instalado
git clone https://github.com/USUARIO/containerlab-dos-pcs.git
cd containerlab-dos-pcs
sudo containerlab deploy -t dos-pcs.clab.yml

8.3 Publicar una imagen propia en GHCR

Si necesitás agregar servicios o herramientas a una imagen base, podés crear un Dockerfile, construir la imagen localmente, etiquetarla y publicarla en GitHub Container Registry. Ejemplo ilustrativo:

Dockerfile de ejemplo
FROM debian:bookworm
RUN apt-get update && apt-get install -y --no-install-recommends \
    iproute2 iputils-ping curl tcpdump dnsutils \
    && rm -rf /var/lib/apt/lists/*
CMD ["sleep", "infinity"]

Construí y probá primero la imagen local. Después, autenticá Docker contra GHCR usando un token personal con los permisos necesarios o un método de autenticación recomendado por GitHub.

Build, tag y push
docker build -t lab-tools:1.0 .
docker run --rm lab-tools:1.0 ip -br addr

docker tag lab-tools:1.0 ghcr.io/USUARIO/lab-tools:1.0
echo "$GHCR_TOKEN" | docker login ghcr.io -u USUARIO --password-stdin
docker push ghcr.io/USUARIO/lab-tools:1.0
Token: definí GHCR_TOKEN en tu entorno de forma segura antes de ejecutar el login; no escribas el token directamente en el comando, no lo guardes en Git y no lo compartas. Usá el alcance mínimo necesario (por ejemplo, lectura para descargar y escritura para publicar) según el método de autenticación elegido.

8.4 Usar la imagen publicada en el YAML

Una vez publicada y accesible para el host, referenciala desde el nodo:

Fragmento YAML
nodes:
  pcA:
    kind: linux
    image: ghcr.io/USUARIO/lab-tools:1.0

Si el paquete GHCR es privado, cada host que deba descargarlo necesita autenticarse con permisos de lectura. Para laboratorios compartidos, publicar una imagen solo cuando corresponda y revisar que no contenga credenciales, datos sensibles ni configuraciones internas.

8.5 Buenas prácticas de versionado

  • Usá etiquetas explícitas como 1.0, 1.1 y 1.2, y describí los cambios en el README o en Releases.
  • Fijá versiones de imágenes para prácticas repetibles; evitá depender sin control de latest.
  • Versioná YAML, Dockerfile y documentación; no versionés capturas PCAP sensibles, claves, tokens ni artefactos grandes sin necesidad.
  • Incluí instrucciones de despliegue, prueba y destrucción, además de requisitos de RAM, CPU y puertos.
09 · Operación

Tips y troubleshooting

La imagen no descarga

Comprobá DNS, conectividad HTTPS al registry, nombre de imagen, tag y permisos del paquete GHCR.

La topología no despliega

Validá indentación YAML, nombres de interfaces, endpoints de enlaces y que el usuario tenga permisos para el runtime.

Los nodos no se hacen ping

Inspeccioná ip -br addr, rutas, estado de interfaces, logs y el nombre real del contenedor.

La GUI no conecta

Verificá estado de la API, endpoint, resolución DNS, firewall, certificado TLS y CORS cuando corresponda.

Falta memoria

Empezá con pocas instancias y herramientas Linux livianas. Supervisá free -h, docker stats y espacio en disco.

Limpiar el laboratorio

Usá containerlab destroy -t archivo.clab.yml y verificá que no queden contenedores o recursos residuales.

Comandos de diagnóstico útiles

Operación básica
containerlab version
docker ps -a
docker images
docker logs NOMBRE_CONTENEDOR
docker exec -it NOMBRE_CONTENEDOR ip -br addr
docker stats
free -h
df -h
Flujo recomendado: editar YAML → revisar el diff en Git → desplegar → validar conectividad → guardar resultados/documentación → destruir el laboratorio si ya no se necesita.
